# T4dataset records

T4dataset record tables are generated by
[t4dataset-generator](https://github.com/tier4/t4dataset-generator), which reads T4 scenes
through [t4-devkit](https://github.com/tier4/t4-devkit) and writes the table this repository
reads. See [dataset records](design.md) for the ownership split and the read side.

## Generating a table

```bash
cd t4dataset_generator

uv run t4records generate \
    --config configs/generate/t4dataset.yaml \
    --data-root /workspace/data/t4dataset \
    --out-file /workspace/records/t4dataset.parquet \
    --workers 16

uv run t4records inspect /workspace/records/t4dataset.parquet
```

One table serves detection3d, segmentation3d and multi, because they train against the same box
taxonomy and every model selects its databases on the reader side. Pseudo labelled corpora get
their own table: their masks are regenerated whenever the teacher changes, and they live under a
different data root.

| Table | Contents | Data root |
| --- | --- | --- |
| `t4dataset.parquet` | the human labelled databases | `data/t4dataset/` |
| `t4dataset_pseudo.parquet` | the pseudo labelled databases | `data/t4dataset/pseudo_large/` |

## What the generator decides

- which scenarios belong to train, val and test, from its database configs
- how many preceding lidar frames each sample carries, `max_sweeps` per database
- which samples are kept, `sample_steps` per database
- how a raw annotation label becomes `box3d_label_name` and `box3d_label_index`

Changing any of those means regenerating the table. Selecting databases, splits and supervision
coverage stays a configuration change here.

## Adding a database

Add a database config to the generator with its release version, point feature layout, sweep
settings and the scenarios of every split, then list it in the generation config and in the
`configs/records/` corpus configs that should train on it.
